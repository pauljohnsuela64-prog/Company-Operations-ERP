## Report definitions and filters

`finance_reporting.py` normalizes year/status/category/department/search once and
builds Decimal aggregates from the exact returned records. Summary, report page
and XLSX share that path. Existing readers remain available to other callers.

Total expense amount/count includes all matching states, including CANCELLED,
as before. Only PAID contributes to spending, monthly paid and category paid
breakdowns. Screen notes explain that distinction. No accounting interpretation
of total expenses as disbursed cash is introduced.

Year uses expense_date, never paid_at. The summary/report/export defaults to the
current year; the expense list defaults to all dates. Invalid filters fall back
to existing defaults instead of overflowing MySQL bindings or workbook filenames.
IDs are bounded positive signed INTs; years are bounded valid calendar years.
Status and category/department filters intersect search. `department_id=none`
selects departmentless expenses. Filter selectors use existing Bootstrap patterns,
including inactive historical master records, without redesigning navigation.
The export link retains filters; filtered workbooks record them in Summary D1/E1
without moving existing rows, headings, sheets or currency formats.

Budget views include only existing applicable department/year budgets. Their paid
totals exclude departmentless and missing-budget spending. The label/notice now
makes that coverage explicit. Example verified by tests: total annual paid 1.20
includes 0.30 against a listed budget, 0.40 in a missing-budget department and
0.50 departmentless. The listed budget's spent amount remains 0.30; it is not
incorrectly presented as the global paid total. Negative remaining balances from
existing budget reductions remain visible, not clamped or silently repaired.

The dashboard Finance card is an all-date work queue. Counts were checked against
the actual all-date Finance data, with unrelated dashboard readers isolated in
the test. Its label says all dates and its View link filters APPROVED expenses.
Separate screen requests may legitimately differ after new commits; this step
does not freeze all dashboard/modules at one cross-request timestamp.

## XLSX security and response handling

Finance has one workbook generator / export endpoint. `safe_text_cell` is applied
to expense number, category code/name, department/supplier name, PO number,
description, reference number and optional filter text. It is not applied to
numeric amounts/counts, dates, fixed headings, generated month labels, trusted
status/payment enums or application-generated formulas.

Formula-like text beginning '=', '+', '-', '@', including whitespace/control/BOM
prefix variants, is serialized with an explicit XLSX string type. No visible
apostrophe is prepended and ordinary valid text is preserved. XML-incompatible
controls/surrogates are shown as printable escaped spelling rather than making
the workbook fail. XML readers normalize CR to LF; tests account for that normal
XML behavior. Numeric cells, date cells, existing four sheets/column headings and
currency formatting remain intact. No Finance formulas currently need execution;
the helper does not disable formulas intentionally generated outside text fields.

Tests reload actual generated bytes with openpyxl and verify string cell types,
no malicious formula cells, numeric/date types and formatting. Payloads include
HYPERLINK, '=', '+', '-', '@', spaces, tabs, CR/LF, BOM, zero-width/NBSP prefixes,
NUL and vertical-tab controls.

Export still requires fresh finance.view authorization. Anonymous, denied and
revoked users cannot export; a finance.view-only user can export but cannot
mutate. Responses remain XLSX attachments with a bounded year-based filename;
Cache-Control is now `private, no-store`. Global CSRF remains unchanged for writes.

## Workflow and preserved protections

Only Finance read/report functions changed. An AST comparison against the starting
commit verified that write routes, payment repository, Decimal validators and
existing audit hooks are untouched. The complete create -> edit -> approve -> pay
lifecycle and a separate cancellation were exercised through real routes. Report
state/amounts update after commit; repeated completed pay/cancel attempts add no
success audits. Generated XLSX reflects the resulting PAID state and safely
stores a formula-like description.

Budget previews now tell users to refresh after budget changes and that payment
rechecks eligibility. The preview remains advisory. Step 1 locks expense -> annual
budget and recalculates current spending under READ COMMITTED; no reservation or
preview-based authorization was introduced. Two different created expenses can
still represent duplicate paperwork; deduplication by invoice/reference needs a
separate approved policy. Duplicate payment of the same expense remains blocked.

## Financial policies requiring approval — not implemented

1. Recommend rejecting reductions below already-paid spending, checked after the
   budget lock with a fresh aggregate. Define an explicit authorized exception /
   history process if reductions must be possible.
2. Recommend keeping department/year keys stable once paid spending exists;
   create a new allocation rather than silently reassigning historical budgets.
   Any approved migration/override requires lock-order and historical reporting review.
3. Decide whether future expenses must have a department or use an explicit
   unallocated process. Current departmentless no-budget-control handling remains.
4. Do not reserve approved/unpaid expenses without an approved commitment policy.
   Clarify expectations when approvals exceed available funds; current payment
   enforcement, not approval, controls actual paid spending.
5. Define payment attribution/reconciliation requirements before adding paid_by,
   external references, reconciled states or discrepancy handling. Current PAID
   means a manual ERP state transition, not a bank-confirmed transaction. paid_at
   and best-effort actor audits do not constitute a reconciled accounting ledger.
